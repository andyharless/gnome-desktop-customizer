## SKILL.md

### 1. nautilus-python `MenuProvider` signatures were reversed

**Before:** Said GNOME 42 uses `get_file_items(self, files)`, and that "older tutorials" show a `get_file_items(self, window, files)` form that some GNOME 43+ builds dropped.

**After:** Describes the two API generations separately:

| Nautilus | nautilus-python | Typelib | Signatures |
|---|---|---|---|
| 42 (Ubuntu 22.04, GTK3) | 1.x | `Nautilus 3.0` | `get_file_items(self, window, files)`, `get_background_items(self, window, current_folder)` |
| 43+ (Ubuntu 24.04+, GTK4) | 4.x | `Nautilus 4.0` | `get_file_items(self, files)`, `get_background_items(self, current_folder)` |

The example code now starts with `gi.require_version("Nautilus", "4.0")`, and there's a note on how to adapt it for 42.

**Why:** The old text had the versions backwards. Nautilus 43 and nautilus-python 4.0 removed the `window` parameter along with the GTK4 port. Someone on 22.04 who followed the old example would get a method with the wrong arity, and since the menu entry just silently fails to appear, that's hard to diagnose. Without `gi.require_version`, PyGObject also prints a warning, and on systems with more than one typelib installed it may load the wrong one.

### 2. Menu-item icons and silent failures

**Added:** Menu items no longer show icons in GTK4 Nautilus (43+). A signature mismatch produces no visible UI error.

**Why:** The workflow's intro gives "icons" as a reason to use nautilus-python, which doesn't hold on 24.04. The silent-failure note explains why checking the signature should come first when debugging.

### 3. `nautilus --no-desktop` replaced

**Before:** `nautilus -q; nautilus --no-desktop` to see extension exceptions.
**After:** `nautilus -q; nautilus` run from a terminal.

**Why:** `--no-desktop` belonged to Nautilus's old desktop-icons feature, which was removed years before GNOME 42. The option is no longer recognized there, so the suggested command would just fail. Running plain `nautilus` from a terminal is enough to see Python tracebacks.

### 4. Example keyboard shortcut changed

**Before:** `binding '<Control><Alt>t'`
**After:** `binding '<Super><Alt>m'`, plus advice to check for conflicts (`gsettings list-recursively | grep -F '<binding>'`) and to use the next unused `customN` path when appending.

**Why:** `Ctrl+Alt+T` is Ubuntu's default "open terminal" shortcut. A new binding with the same combo would conflict with it, and an agent copying the example literally would break a shortcut the user relies on. `Super+Alt+M` isn't bound by default on stock Ubuntu. The conflict check is the more important part, since any example could clash with a user's own bindings. The `customN` note fills a gap in the existing "append rather than overwrite" advice, which didn't say what the new path should be.

### 5. Startup Applications in GNOME Tweaks

**Before:** "`gnome-tweaks` → Startup Applications" given as the GUI route with no version caveat.
**After:** Marked as GNOME 42 only; Ubuntu's standalone `gnome-startup-applications` app given as the alternative.

**Why:** Newer GNOME Tweaks releases removed the Startup Applications panel, so on 24.04 the instruction points to a panel that doesn't exist. This is the kind of version difference the skill promises to call out.

### 6. GNOME Shell extension details

**Added:**
- `gnome-extensions install <file.zip>` and `gnome-extensions list --enabled` in the CLI list.
- The package the extensions.gnome.org browser integration needs: `gnome-browser-connector` (`chrome-gnome-shell` on 22.04).
- On Wayland, a *newly installed* extension isn't picked up until the user logs out and back in. Enabling or disabling an already-installed one applies live.

**Why:** The old text said "needs the browser connector" without naming the package, and its CLI list could manage extensions but not install one from a zip. The Wayland note matters because Ubuntu uses Wayland by default. Without it, "install then enable" looks broken ("extension doesn't exist") until the user logs out and back in.

### 7. File-location boundary made consistent with the backup commands

**Before:** "Everything in this skill lives under `~/.config`, `~/.local/share`, or `~/Templates`."
**After:** Adds "(plus backup files written to `~`)".

**Why:** The skill's own `dconf dump` backup example writes `~/gnome-backup-YYYYMMDD-*.conf`, which is outside those three directories. An agent following the rule strictly might refuse to take the backup or put it somewhere odd. Changing the rule was a smaller edit than moving the backups, and backup files in `~` are easy for users to find.

### 10. "Device-bridge/remote-computer" wording

**Before:** "...this works from a session linked to your desktop via Claude's device-bridge/remote-computer features..."
**After:** "...a remote or SSH session into that machine works too, though some changes need your graphical session's environment to apply."

**Why:** "Device-bridge" isn't a product name a reader can look up, and the original sentence suggested everything works the same remotely. That isn't quite true. `gsettings`/`dconf` writes need to reach the user's session D-Bus, and commands like `nautilus -q` or `gnome-extensions enable` act on the running graphical session. Over plain SSH, some of these need `DBUS_SESSION_BUS_ADDRESS` (and sometimes `DISPLAY`/`WAYLAND_DISPLAY`) set correctly.

### 11. File-location promise

The "What it won't do without asking" list got the same backup-file clarification as item 7, so the README and SKILL.md agree.
